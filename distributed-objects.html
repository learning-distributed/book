Distributed Systems: Principles and Practice

Distributed Objects

Quorums and Versions

Our overarching goal in the first two parts of this book is to learn how to build fault-tolerant systems from faulty components communicating over faulty networks. In a previous chapter, we saw how the primary-backup approach can be used to tolerate the complete failure of some nodes. However, to call the system as a whole "fault-tolerant" would be an overstatement. The view server was a single point of failure, and the system would permanently cease functioning if the wrong server nodes failed at the wrong time, even when there were ample "standby backups."

In this chapter, we will take the first step towards our goal by building two different distributed objects: an add-only set and a read/write register. In these protocols, we will utilize quorums and versions, which are a fundamental building blocks of Paxos and other algorithms we will see throughout the remainder of this book.

Definition: Quorum

A quorum is a set of nodes which can collectively execute an operation.

The most commonly used quorum is the majority quorum where any majority of nodes can vote to execute an operation. Because any two majorities overlap, there will always be at least one node to carry forward knowledge of the operation's execution to any other quorum.

Aside: Quorum Systems

A quorum system is the set of all possible quorums that can vote to execute operation. For example, if the set of servers is \(\Sigma\), then \(\left \{ Q \subseteq \Sigma : 2 \cdot |Q| > |\Sigma| \right \}\) is the majority quorum system.

Often, when we replicate data in a distributed system, as we did in the primary-backup approach and as we'll do when writing to quorums, we will need to deal with conflicting updates to the same piece of distributed state. A version is metadata that is attached to a portion of local state as well as updates to that local state that describes which updates should take precedence. Versions are similar to logical clocks in that they are totally ordered, but unlike logical clocks, the versions attached to updates must be unique.

Add-only Sets

In this chapter, we will build a protocol for a distributed set that supports two operations: \(\texttt{add}(e)\), which adds the element \(e\) to the set and \(\texttt{contains}(e) \to b\) which returns the boolean \(b\) indicating whether \(e\) is an element of the set. As usual, our nodes will be divided into clients and servers. There is a fixed number of servers, \(n\), and the addresses of the servers are known to all clients and each other. However, the number of clients is unbounded and their addresses are not known in advance. We assume the Standard Fault Model: nodes can fail by crashing but otherwise follow the protocol we specify, and messages can be arbitrarily delayed and reordered but not altered by the network.

The goal of our protocol is to tolerate the failure of as many servers as possible while preserving linearizability. From the perspective of the \(\texttt{add}\) and \(\texttt{contains}\) operations, our system should be indistinguishable from a single-node, single-threaded process.

Building the Protocol

Using the goals we've set for ourselves as guides, let's build a protocol. In order to tolerate the failure of as many servers as possible, the client will implement \(\texttt{add}(e)\) by broadcasting \(e\) to all servers. Each server will maintain a local set, and upon receiving a new element, will add the element to its local set and respond to the client. Before returning, the client should wait for responses from the servers. However, it cannot wait for all of them; if one of the servers fails, it would be stuck waiting forever. It will instead wait for a majority of the servers to respond.

Similarly, the client will implement \(\texttt{contains}(e)\) by broadcasting a query for \(e\) to all servers. Each server will respond with a boolean indicated whether \(e\) is in its local set. The client again waits for a majority of servers to respond. If any server responded \(\texttt{true}\), the client returns \(\texttt{true}\); otherwise, if all servers that responded responded \(\texttt{false}\), the client returns \(\texttt{false}\).

<Protocol v1 specification>

Now let's see if this protocol preserves linearizability. First, we will prove that if a client executes \(\texttt{contains}(e_0)\) after an \(\texttt{add}(e_0)\) already completed, then it will return \(\texttt{true}\). When \(\texttt{add}(e_0)\) finishes, we know that the local sets of a majority of servers contain \(e_0\). And when the client executes \(\texttt{contains}(e_0)\), it must query a majority of servers. Because any two majorities have non-empty intersection, at least one of the servers it queries will have \(e_0\) in its local set and respond with \(\texttt{true}\). Therefore, the result of \(\texttt{contains}(e_0)\) will be \(\texttt{true}\).1

Aside: Flexible Quorums

The protocol we've described used majority quorums for both \(\texttt{add}\) and \(\texttt{contains}\). While this arrangement allows the protocol to tolerate the most failures while maintaining availability, it is not the only possibility.

The important fact we used in the argument above is that any \(\texttt{add}\) quorum overlaps with any \(\texttt{contains}\) quorum. That is, if \(\mathcal{Q}_\texttt{add}\) is the quorum system used by the \(\texttt{add}\) protocol and \(\mathcal{Q}_\texttt{contains}\) be the quorum system used by \(\texttt{contains}\), then the property we require is \(\forall Q_A \in \mathcal{Q}_\texttt{add} \forall Q_C \in \mathcal{Q}_\texttt{contains} : Q_A \cap Q_C \ne \emptyset\).

We could, for example, use quorums of size \(n\) for \(\texttt{add}\) and size 1 for \(\texttt{contains}\). This would allow reading from any single server, but if any server failed, no other elements could be added to the set! Similarly, we could use quorums of size \(n - 1\) for \(\texttt{add}\) and size 2 for \(\texttt{contains}\). This would allow reading from any pair of servers, and we could still add elements to the set even after a single server failure.

In general, when we're using a quorum system where all quorums are of a fixed size, that size must be larger than \(f\) (the number of failures we wish to tolerate). And because the \(\texttt{add}\) and \(\texttt{contains}\) quorums must overlap, \(f\) is maximized at \(\left \lfloor \frac{n-1}{2} \right \rfloor\) when both operations use the majority quorum system.

Now comes the question: are we done? Does the simple protocol we've built fully guarantee linearizability. Think about it, take some time, and try to justify an answer. If the protocol does guarantee linearizability, you should try to prove it. If the protocol doesn't guarantee linearizability, you should try to produce an execution of this protocol which couldn't have been produced by a single server executing operations sequentially.

The answer is that we are not done. The protocol above has a flaw. Our \(\texttt{contains}\) protocol is guaranteed to return \(\texttt{true}\) if an \(\texttt{add}\) for the same element finished executing but is allowed to return any value if an \(\texttt{add}\) is in progress. This in itself is fine, but if two \(\texttt{contains}\) operations are executed sequentially during the execution of an \(\texttt{add}\), we may run into problems. As a concrete counter-example to linearizability, let's look at a trace where there are three servers: \(\sigma_1\), \(\sigma_2\), and \(\sigma_3\).

  1. \(\texttt{add}(e_0)\) starts on one client, \(c_1\), and the request is only delivered to \(\sigma_1\). The other requests are delayed in the network.
  2. Another client, \(c_2\), executes \(\texttt{contains}(e_0)\) and gets responses from \(\{\sigma_1, \sigma_3\}\), so the result is \(\texttt{true}\).
  3. Yet another client, \(c_3\), executes \(\texttt{contains}(e_0)\) and gets responses from \(\{\sigma_2, \sigma_3\}\), so the result is \(\texttt{false}\).
  4. The remaining requests for both \(\texttt{add}\)s are delivered, as are the responses. The \(\texttt{add}\)s both complete (but it's too late).

This is a counter-example to linearizability because our third client observed that \(e_0\) was missing from the distributed set after the second client had already observed it was present.

Fortunately, we've already implemented a protocol that guarantees exactly this property! This is the exact property that \(\texttt{add}\) guarantees. We will therefore modify the protocol for \(\texttt{contains}\). Read/Write Registers

Now that we've built a distributed set, let's look at another (deceptively) simple distributed object: a distributed register. This register will support two operations: \(\texttt{write}(v)\) which sets the value of the register to \(v\) and \(\texttt{read} \to v\) which returns the current value of the register. The register only holds a single value and \(\texttt{write}\) overwrites that value completely.

Other than the operations we'd like to support, the setup is the same as for the distributed set. We have \(n\) servers and would like to tolerate as many failures as possible while maintaining availability. We must guarantee linearizability in all cases.

A Naïve Approach

Given that this object looks so much like the \(\texttt{add}\)/\(\texttt{contains}\) set we just built, can we use a very similar approach? Let's try writing to and reading from a majority. In this naïve protocol, when executing \(\texttt{write}(v_0)\), the client sends \(v_0\) to all servers. Each server sets its local register value to \(v_0\) and replies. The client waits for responses from a majority before returning.

When executing a \(\texttt{read}\), the client asks all servers for their local register state and waits for a majority to reply. But now we already have a problem. If the client observes multiple values when reading from a quorum, which should it return?

To make this situation concrete, let's look at a trace with three servers: \(\sigma_1\), \(\sigma_2\), and \(\sigma_3\).

<Space time diagram here>
  1. One client successfully executes \(\texttt{write}(v_1)\) after getting replies from \(\sigma_1\) and \(\sigma_3\). (Its message to \(\sigma_2\) is delayed in the network).
  2. Another client then successfully executes \(\texttt{write}(v_2)\) using \(\sigma_2\) and \(\sigma_3\). (Its message to \(\sigma_1\) is delayed).
  3. Another client then executes a \(\texttt{read}\) and gets \(v_1\) from \(\sigma_1\) and \(v_2\) from \(\sigma_2\). In order to preserve linearizability, it must return \(v_2\), but there is no way to guarantee that.

Versioning Updates

Obviously, we need a way for reading clients to choose between the values it sees during a \(\texttt{read}\) and decide which value to return. To that end, when writing a value to the register, each client will attach a version to the value, and the servers will maintain the latest value and version they've received from in any \(\texttt{write}\). Importantly, versions must be totally ordered so clients can always decide which value "wins." Each client keeps a version number for the most recent value it wrote to the shared set and picks a new, larger version when initiating a \(\texttt{write}\). When reading, a client waits for responses from a majority with their local values and versions and returns the value with the largest version.

This just leaves one problem: what if two different clients write different values with the same version? Then, a client trying to read the value stored in the distributed register might see \((v_1, 3)\) and \((v_2, 3)\) (where \(v_1 \ne v_2\)) in the set of responses it receives. We haven't solved the problems with the naïve approach at all!

In order to fix this problem fully, we will need to give each client a unique set of versions to use. To that end, we will assume that each client has a unique "name"; this could be an IP address, the MAC address for its network card, a name provisioned by the system administrator, or a (very large) randomly generated number.

Versions will be tuples consisting of a version number – which is just a natural number – and the client's unique name. For example: if we have three clients with unique names \(\texttt{client1}\), \(\texttt{client2}\), and \(\texttt{client3}\), \(\texttt{client1}\) would use the versions \((1, \texttt{client1})\), \((2, \texttt{client1})\), \(\ldots\). These tuples are compared lexicographically; so \((2, \texttt{client1}) > (1, \texttt{client2})\). Assuming that \(\texttt{client2} > \texttt{client1}\), \((2, \texttt{client2}) > (2, \texttt{client1})\). It doesn't matter how the clients' names are ordered, as long as they are totally ordered. Here, we're just comparing the clients' unique names as strings.

Now, using our version tuples, clients can always choose between the values they see when reading from the distributed register. Similarly, servers can make sure that they only store the latest version/value. Our protocol now looks like this:

Ensuring Linearizability

We still have a problem with our writing protocol, though! Each client maintains its own local version number, and there's no guarantee that a client will write using a version that is larger than the version currently stored in the distributed register. If one client writes \(v_1\) and then after that write is complete, another client writes \(v_2\), a client that reads the value of the register after the write of \(v_2\) completes must return \(v_2\).

DIAGRAM HERE SHOWING THE THREE OPERATIONS ON A TIMELINE

In order to fix this, we need to make sure that the write protocol first discovers the latest version written to the distributed register and then writes its value using a version that is strictly larger. When writing, the client will first read the versions stored at a quorum. It will take the largest version number it received from any server, increment it, and use its own name to create a version tuple that is guaranteed to be larger than any value that was previously written.

We are almost done. There is one last problem with this protocol, and it is the exact same problem that we saw with the add-only set! Namely, if a client reads a value that is currently in the process of being written to a majority, there is no guarantee that a later client will read a value as fresh. This would again violate linearizability.

We can fix the problem with the reading protocol with the exact same technique we used previously. We will add an extra phase to the reading protocol in which the client writes the value it read to a quorum.2 Importantly, the client sends this value to the servers using the version it observed when reading from the quorum. We aren't trying to write the value anew; we're merely ensuring that knowledge of the latest value and version we read is present at a quorum of servers.

With this fix in place, the protocol is actually complete! Now, the \(\texttt{read}\) and \(\texttt{write}\) protocols look remarkably similar. Both protocols consist of two phases. They start by reading the current value/version stored at a quorum, and then they write a value and version to the quorum. The \(\texttt{read}\) protocol writes the largest version and value it saw in the first phase. The \(\texttt{write}\) protocol writes its input value to a quorum, using a version that is larger than any it saw in the first phase.

Final protocol

Correctness

In order to show that this protocol guarantees linearizability, we need to show that any execution produced by our protocol is equivalent to some sequential execution of operations that is compatible with the real-time ordering of input and output operations. In this case, constructing sequential execution is very simple: given an execution of our protocol, we arrange all operations according to the version observed in the distributed execution. For \(\texttt{write}\) operations, this is the version that the client used to write the value to the distributed register. For \(\texttt{read}\) operations, this is the version of the value that the client read. Furthermore, we will order a \(\texttt{write}\) before all \(\texttt{read}\)s for the same version. \(\texttt{read}\)s which read the same version can be ordered arbitrarily; we will order them according to their start time.

Certainly, this sequential execution produces the exact same results that our distributed execution did. All that we need to show is that this ordering of operations is compatible with the real-time ordering of events as they actually happened. This argument is straight-forward and relies on quorum intersection.

Suppose there exist two operations \(o_1\) and \(o_2\) where \(o_1\) appears before \(o_2\) in our manufactured sequential execution, but during the actual distributed execution \(o_2\) finished before \(o_1\) began. We will show that this leads to a contradiction. Because \(o_2\) appears after \(o_1\) in our total order of events, it must have a version at least as large as \(o_1\). Because \(o_2\) completed before \(o_1\) began, \(o_2\) cannot have a larger version than \(o_1\). During the second phase of the protocol, clients ensure that their version is sent to a quorum. During the first phase of the protocol, clients read the version from a quorum, and the version for the operation will ultimately be at least that large. Therefore, \(o_1\) must have a version at least as large as \(o_2\), and so both operations have the same version.

There are now four cases we need to consider: (1) \(o_1\) and \(o_2\) are both \(\texttt{write}\) operations, (2) \(o_1\) is a \(\texttt{write}\) and \(o_2\) is a \(\texttt{read}\), (3) \(o_1\) is a \(\texttt{read}\) and \(o_2\) is a \(\texttt{write}\), and (4) \(o_1\) and \(o_2\) are both \(\texttt{read}\)s. The first case is impossible; each client has its own set of versions to use and ensures that it does not reuse versions. The second case is also not possible; the client would have to read a version which hadn't begun to be written. The third case is impossible because our total ordering was constructed with \(\texttt{write}s\) preceding \(\texttt{read}\)s with the same version. The final case is also impossible because our total ordering was constructed with \(\texttt{read}\)s ordered by their start time, contradicting the assumption that \(o_2\) completed before \(o_1\).

Therefore, we have arrived at a contradiction and our constructed sequential ordering of events is actually compatible with the real-time ordering of events observed during the distributed execution.

Discussion

In this chapter, we saw protocols for implementing two different fault-tolerant distributed objects: and add-only set and a register. Both of these protocols utilized quorums to read and write information to a distributed object in a way that is fault-tolerant. Because we used majority quorums, we could tolerate the failure of a minority of servers. Moreover, both protocols guaranteed linearizability in all circumstances, no matter how many servers fail. The distributed register protocol used versions to establish an ordering between overlapping operations.

The distributed register protocol we saw is actually a well-known protocol due to Attiya, Bar-Noy, and Dolev, usually referred to as the ABD protocol [1].

Interestingly, the protocols we built in this chapter were all strictly client-coordinated. That is, there was no server to server communication. This will not be the case for many other distributed protocols we see in this book. The protocols we saw in this chapter also executed in bounded number of rounds of communication with a quorum of servers.
