Distributed Systems: Principles and Practice

Consensus and State Machine Replication

In this chapter we will introduce the core problem of this section – distributed consensus. Informally speaking, the consensus problem is about getting a set of nodes to agree on a single value. Unlike consensus among people, the problem isn't disagreement due to different preferences or conflicting personalities. The core difficulties are the same as with the other protocols we've been building: asynchrony, unreliable message delivery, and partial failure.

Classically, the consensus problem is studied with a system of \(n\) nodes. Each node is initialized with an input value and is equipped with a special output action to decide a value. The consensus problem puts the following requirements on the values that nodes output.

Definition: Consensus

  • Agreement: All decided values must be equal.
  • Integrity: Any value that a node decides must have been the input value to some node.
  • Termination: All correct nodes must eventually decide some value.
You will sometimes see various presentations that add additional requirements like "Validity" to consensus, but these alternative formulations are generally equivalent to the one we have shown.

We again assume our Standard Fault Model. In this fault model, a correct node is one that doesn't crash. If we were working with a fault model that allowed so-called Byzantine failures, where some nodes may be actively malicious, the above definition would have to be modified to only place requirements on the output values of correct (i.e., non-Byzantine) nodes. Malicious nodes can and will output whatever they like.

From a certain perspective, this problem is not all that different from distributed register we built in the previous chapter. The input values that our consensus nodes receive are like the values written to the register, and when our consensus nodes decide a value, that's like reading the value of the register. There is a critical difference, though. Our distributed register was allowed to return different values to different readers; the distributed register had a "last writer wins" policy. Our consensus nodes are implementing a shared register where the first writer has to win – only one value can be decided.

In multithreaded programming, consensus can be accomplished using the compare-and-swap operation on a shared atomic register. Assuming the register is initialized with a special null value (which is not in the domain of possible input values), each thread can execute a compare-and-swap register, swapping in its input value to the register if the current value is null. Then, each thread reads the value of the register and outputs that value. Exactly one of the compare-and-swap operations will succeed, and all threads will output that value.

In the distributed environment, though, we don't have shared atomic registers. We only have message passing over an imperfect network. We saw that in such an environment, it was possible to build a register which could be written and read. Unfortunately, that register is of no use to us in solving consensus. Even more unfortunately, solving the consensus problem in our Standard Fault Model is impossible. We will eventually do the (almost) impossible, but before we do that, let's see why the consensus problem is so important.

State Machine Replication from Consensus

The first thing to establish is why getting servers to agree on a single value is so important. At first glance, this seems less than useful. Even if we run many separate instances of consensus, we would still have a system where every value can only be written once. There may be a certain beauty to a write-once database, where all decisions are permanent monuments etched in stone for future generations to admire. But a useful application it is not.

The key trick, however, is that instead of having our nodes agree on data, they instead will agree on operations. We have our servers run many instances of consensus, where each instance is numbered and associated with a single slot in an operation log (often just called a "log"). Importantly, each of these operations must be deterministic. If nondeterministic operations are required, they must be made deterministic (i.e., by making all non-deterministic choices for the operation) before being added to the operation log.

Each of our consensus servers can then execute these operations locally as they are decided. The servers maintain local state which the operations can access. The operations can also specify output events to, for example, send results to clients of our system.

This idea of reaching agreement on a series of deterministic operations to execute is known as the state machine approach [1]. Our nodes maintain state that can be continuously updated by individual operations, which appear from the clients' view to be executed atomically. This is a very general and powerful model, as we can represent any deterministic, interactive application as a series of operations to be executed on a state machine. And because the underlying consensus protocol should tolerate the failure of some of our nodes, when we replicate a state machine using consensus, the resulting system will be able to tolerate the same failures.

Readers familiar with file systems will recognize that this idea of an operation log is similar to the idea of a journal, where operations are written before being actuated on data. And indeed, our consensus-based log of operations will need to solve many of the same problems that journaled file systems do. For example, as we've described it so far, our operation log will grow without bound as more and more operations are executed. This will eventually consume all available memory, even if the actual state stored in the state machine remains small. Therefore, we will need a mechanism to do garbage collection on the log and purge log entries (i.e., consensus instances) when we're certain they're no longer needed.
