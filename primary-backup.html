Distributed Systems: Principles and Practice

Primary-Backup Replication

  • Recall how our RPC protocol does not handle node failures.
  • Our goal in this chapter is to begin handling node failure.
    • Spoiler: This chapter will not completely satisfactorily handle node failures. We will get there when we discuss consensus in later chapters.
  • So you want to handle a node failure. What happens when a node fails?
    • Whatever that node would have done if it didn't fail, some other node now needs to do.
    • So you need more than one node. And you need more than one node that is "ready" to do whatever the failed node was doing.
  • If all you have is compute (eg stateless RPC), then this is pretty easy. You can have a pool of servers. Since requests are stateless, any server can serve any request. If a server fails, no problem as long as there's still at least one server remaining.
    • All the nodes in the pool are ready at any time to answer any client's stateless requests.
  • Harder if RPCs are stateful!
    • Say we have one client C and two servers S1 and S2 and our goal is to use the two servers to build a fault tolerant key-value store that still works if either server fails.
    • We can't just do what we did for stateless RPCs and say that any server can answer any request, because the servers have to keep track of the current state of the key-value store. If C executes put("foo", "hello") on S1 and gets a response, and then C executes get("foo") on S2, then C expects the answer to be "hello", but S2 has no idea about the first request.

  • You can think of a RPC response from the system as a promise never to forget that the RPC happened. If a node fails, that can't cause the system to forget that the RPCs executed by that node happened.
    • "You shouldn't make promises you can't keep." -- a server shouldn't respond to a client request without knowing that the RPC will survive the server's own failure.
    • And that means the server has to tell another server about the request before executing it.
    • Similarly, a server must be sure it has the most recent state before executing new client requests on that state.
  • There are many ways to design a protocol so that the server "tells another server" before responding to the client. In this chapter we study a relatively simple technique called primary-backup replication.

Primary-Backup version 0

  • There are any number of clients.
  • There are two servers, called the primary and the backup.
  • Clients send requests to the primary.
  • The primary sequences the requests and forwards them in order to the backup.
  • The backup execute each request it receives from the primary in order and responds to the primary to tell it that the request is now saved on the backup.
  • Once the primary hears that the next forwarded request is executed on the backup, it can execute it locally and respond to the client who originally sent the request.

With this protocol, the results of each requested are reflected on both servers before the client gets a response. This is good because it means in theory the backup has everything it needs to takeover if the primary fails.

Primary failover

Suppose the primary fails. The idea was that the backup should take over. But how does that actually happen?

  • Since there are only two servers, if the primary fails, then the backup will be all alone. So if we want the system to keep executing requests, then the backup will have to do them by itself. This means the system will not tolerate any further node failures, but let's say we're ok with that.
  • Clients were sending their requests to the primary. If the primary fails, they will not get any answers but will have no idea why. The backup has no way to take over.
  • We can adjust the protocol so that clients send their requests to both the primary and the backup. As long as both nodes are up, the backup can just ignore client requests except for those that are forwarded by the primary. (Exercise: why can't the backup just execute the requests it receives from clients?)
  • When the primary fails, the backup can take over and start executing requests directly from clients instead.

  • When does the backup know to take over? Maybe when it hasn't heard from the primary in "a while"?
  • What happens if the network dropped a bunch of messages from the primary, so the backup doesn't hear from the primary for a while and decides to take over? But actually the primary is still up. And then the network starts delivering messages again. Once it takes over, the backup should ignore forwarded requests from the primary (exercise: what happens if the backup responds to forwarded requests normally?)

This strategy of having the backup take over when the primary fails seems to work. Notice that the backup is the one who makes the decision about when to take over. The primary can't make this decision because it might have failed!

Backup failover

Now suppose the backup fails. The situation is nearly a mirror image from the case when the primary fails.

  • Again, since there are only two servers, if the backup fails, then the primary will be all alone. So if we want the system to keep executing requests, then the primary will have to do them by itself. This means the system will not tolerate any further node failures, but let's say we're ok with that.
  • The primary can take over when it hasn't heard from the backup in "a while".
  • If the primary takes over but then later starts receiving messages from the backup, it can just ignore them.

This failover procedure also seems to work to tolerate a backup failure. Notice that the primary is the one who makes the decision about when to take over. The backup can't make this decision because it might have failed!

The problem

Perhaps you have noticed a problem with these two failover procedures: they could both happen at the same time! Suppose both the primary and backup are up but the network between them has failed, so they can't communicate. Both the primary and the backup may misinterpret the lack of communication as an indication that the other node has failed, and initiate their failover procedure to take over the system. The result is two nodes that both think they have taken over and can both execute further client requests, violating linearizability. (Exercise: write out a scenario that demonstrates the linearizability violation.)

The issue is that the primary and the backup each have the ability to unilaterally take over the system. This seems necessary in order to tolerate failures, but it leads to a non-linearizable protocol.
