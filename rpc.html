Distributed Systems: Principles and Practice

Remote Procedure Call (RPC)

As we saw in the previous chapter, distributed systems are designed to operate in faulty environments where messages can be dropped, duplicated, and delayed, and machines can crash or run at different speeds. This chapter begins our discussion of how to design systems to tolerate these faults.

The nodes of a distributed system collaborate to solve a common problem. A very common activity in a distributed system is for one node to request that another node do something for it. For example, if you are watching Youtube shorts on your phone, then whenever you swipe down to the next video, your phone (your phone is a node!) sends a request to a server owned by Google (another node) to request the next video. Nodes sending other nodes requests is the bread and butter of a distributed system in action. At companies like Google, nodes collectively send billions of requests per second.

The question we address in this chapter is: how does one node in a distributed system reliably send a request to another node, even in the presence of network failures? (This chapter does not discuss node failures. We will return to those in later chapters.)

Asking another node to do something is somewhat analogous to a procedure call (also known as a function call or a method call) in non-distributed programming. The main difference is that the procedure is executed on a different "remote" node. This abstraction is known as a Remote Procedure Call (RPC), i.e., calling a procedure that runs on a separate machine. The "remoteness" makes an important difference: when a node invokes a remote procedure, a fault can occur in the middle of the invocation (e.g., the network could lose a message, or the server could crash), and the calling node needs to be prepared to handle that fault (e.g., by sending the request again).

As we will see below, there are several nuances to handle in making this process reliable, so designing a protocol using RPCs ends up feeling quite different from organizing a single-node program into a set of procedures. The single-node programmer never has to think "But what happens if I call the function but the call never arrives?" That is exactly the kind of thinking required to design a reliable distributed system with RPCs!

Running Example: Key-Value Store

To make this concrete, we will discuss an example service called a key-value store, which exposes a map-like API to other nodes. An implementation of a key-value store might internally use a map data structure such as a red-black tree or hash table and make its functionality available to remote clients. Key-value stores are common in practice. They are frequently used, for example, as caches for intermediate results or to hold ad hoc data in a database.

We will assume, without loss of generality, that the keys and values of the underlying map are strings. The map-like operations supported are:

  • get(key): returns the current value associated with key
  • put(key, new_value): associates new_value with key; any previously associated value is replaced
  • append(key, more_value): updates the value associated with key to be the old value with more_value appended to the end, and returns this updated value

Also, we assume, again without loss of generality, that clients send only one request at a time; they must receive the reply to their previous request before sending the next request.

The RPC protocol should allow clients to think about an RPC as if it was a local procedure call. In particular, the RPC protocol should satisfy the single-client single-server sequential correctness property:

Later, we will introduce a more sophisticated correctness property called linearizability, which will also specify correct behavior in the presence of multiple concurrent requests and more than one client.

Definition: Single-Client Single-Server Sequential Correctness

If the system consists of one client and one server, and neither the client nor the server fail, and the client sends a sequence of requests one at a time, waiting for each response before sending the next request, then the sequence of responses agree with what would have happened if we had run the procedures locally rather than remotely.

This is a useful specification for client programmers because they can pretend that their code is not distributed, and that invoking an RPC is just like invoking a local procedure. Most programmers are already skilled at reasoning about local code, and this specification removes the need for distributed reasoning. As we will see throughout the book, supporting this abstraction in practice is much more complex on the server side, especially when there are multiple servers and servers can fail.

Naive RPC Protocol

With single-client single-server sequential correctness in mind, let's now turn our intuition about request and response messages into a more precise description of a distributed protocol, which we call "Naive RPC".

  • When the application layer wants to invoke an RPC, then the client sends a request message with the procedure name and argument values to the server.
  • When the server receives a request message, it executes the specified procedure on the given arguments, and sends a response message containing the return value back to the client.
  • When the client receives a response message, it returns the value to the application layer.
  • We make the following assumptions:
    • Nodes do not fail.
    • The application layer will not invoke another RPC until it receives the return value from the previous RPC.

This is our first description of a distributed protocol. It primarily consists of describing what happens when certain events occur, which we call "event handlers". In an implementation, the event handlers become code that runs when the relevant event occurs. In general, if a certain event is not handled by a protocol description, it means it should be ignored. For example, if a Client receives a Request message (which should never happen), it ignores the event, because only the server executes requests in this protocol.

Correctness of Naive RPC

One of our main goals with this book is to teach you to reason about programs where there are failures. Let's consider whether Naive RPC achieves its goal of single-client single-server sequential correctness when the network can arbitrarily delay, drop, duplicate and reorder messages. (We assume no node failures for now.)

If the network delivers each message exactly once, then yes, the protocol is correct. But what happens when there are network errors? This protocol is horribly broken! Here are just a few ways:

  • If any message is dropped, the client cannot make further progress.
  • If the network duplicates a request message so that it is delivered twice, the server will execute it twice, which is wrong for append since appending something twice is different from appending it once.
  • If a response message is duplicated and the second copy is delivered later, then the client may believe that the reply is for some later request.

We will fix all of these problems. Let's start with the first one.

The problem with drops and delays

Consider the situation where the network drops or delays certain messages.

First, suppose the network drops the client's request message.

In this scenario, the client will wait for a response from the server that will never come.

Second, suppose the network delivers the client's request, but then drops the server's response.

Again, in this scenario the client will wait forever for a response.

Finally, it's also possible that the request or the response message get delayed in the network.

In this scenario, the client waits for a long time before the response arrives, but otherwise the system behaves correctly.

All three scenarios involve the client waiting. In the case of the dropped messages, the client will wait forever. In the case of the delayed response, the client can wait for an arbitrarily long time, and the client has no way of knowing how long it should wait. Until the delayed response arrives, the client does not know whether a message was dropped or merely delayed. In other words, while it is waiting, the client cannot distinguish the three scenarios.

But notice one very important difference among the scenarios: in second two scenarios, the request was executed by the server, but in the first scenario, the request was never received by the server, so it was not executed. The client has no way to tell the difference between these two cases! This presents a major challenge for designing systems that tolerate network drops and delays. Clients must be aware of the possibility that their request was actually executed, but the response got delayed or dropped, so they never heard about it.

Handling drops and delays via retransmission

If the client's request message gets dropped, then there is nothing the server can do about it, because the server never even heard about the request in the first place. So the only node that can take action to handle this fault is the client. The basic idea is that the client should try sending the request again, and hopefully the message will be delivered successfully on this second attempt.

Detecting drops in distributed systems

If a message is dropped, it makes sense that a node can handle the situation by sending the message again, but when exactly should the node retransmit the message? Ideally, a node would only retransmit a message when it knows that the message was dropped. Unfortunately, in the standard fault model, it is not possible for a node to know for certain that one of its messages was dropped.

The client can know that its message was delivered if the server's reply is received, so one might think that a node could infer that the message was dropped if the recipient does not respond in a reasonable amount of time. But that is not true! It's possible that the original message is simply delayed for an unreasonable amount of time. Or perhaps the original message was received but the response was dropped. Since these two situations are indistinguishable to the sending node, it has no way to accurately detect that it's message was dropped.

This is a fundamental limitation in distributed systems. We design protocols so that nodes handle dropped messages by retransmitting them, and nodes must retransmit even though they are not sure the messages were dropped. (Of course, if a node is sure its message was delivered, then there is no need to retransmit.)

Let's update the protocol to handle dropped messages:

  • The client repeatedly retransmits each request message until it gets a response.

While this helps with drops, it highlights another problem: if the original request message was merely delayed instead of dropped, the client has no way of knowing that (see note on "Detecting drops"), so it will retransmit anyway. Now there are two copies of the message in the network. If both the original request and the retransmitted request are delivered to the server, then the server will execute the request twice. This does not satisfy Single-Client Single-Server Sequential Correctness, which says each request should be executed exactly once and in the order specified by the application. We will handle these duplicate requests in the next section.

Duplicates

In the standard fault model, the network can duplicate any message. In particular, if the network duplicates the client's request message, then we end up with a similar situation to the previous section: the request is delivered to the server twice, and the server executes it twice, which is wrong.

Consider the scenario illustrated by this timeline diagram:

In this scenario, suppose the initial value of "foo" is "hello". Then the client sends a request to append "world" to the value of key "foo". The request is delivered and the server executes it, updates the value of key "foo" to be "helloworld", and sends a response back to the client with this updated value. Then the network delivers a duplicate of the client's request message again. The server unknowingly executes it again, updating the value of key "foo" to be "helloworldworld" and sending another response to the client. The application layer will be very surprised to learn that its append request was executed twice, since this results in the wrong value being associated with "foo"!

The situation can be even worse if the two response messages get reordered, as illustrated in this timeline diagram:

In this situation, the client receives the response to the duplicated request first, which reports that the new value is "helloworldworld". Since the client was waiting for a response to its request, it will interpret this message as the answer and return this incorrect value to the application layer.

It does not matter whether the reason for the duplicate message is that the client retransmitted it on purpose or that the network duplicated the original request, the solution is the same: the server must detect that the request was already executed and avoid executing it again.

To enable the server to detect duplicate requests, the client can put a unique identifier on each request. Then, the server can remember all the unique identifiers it has already executed, and avoid re-executing them.

A related issue occurs when response messages are duplicated. Consider the following scenario:

The client first sends a get request for key "foo", which is delivered to the server, who executes it and returns the value "hello". Then the client sends a second request to append value "world" to key "foo". At this point, the network redelivers a copy of the first response message. The client will interpret this message as a response to its second request, and return the (wrong) value to the application layer.

The problem is that the client has no way to distinguish responses to different requests. We can solve this problem by reusing the unique identifiers the client puts on its requests to help the server deduplicate them. Whenver the server sends a response message, it can include the unique identifier of the corresponding request. Then, when the client is waiting for a response to a particular request, it can ignore all response messages with a different unique identifier.

To summarize, in this section we have made the following adjustments to the Naive RPC protocol.

  • The client puts a unique identifier on each of its requests. "Unique" means this client never sends two different requests with the same identifier. When the client retransmits a request, it reuses the same identifier as when it first sent the original copy of the request.
  • The server keeps track of the identifiers of all the requests it has ever executed. When the server receives a request, it firsts checks to see if the request identifier is already in its set of executed requests, and if so, it does not re-execute the request. Otherwise, it executes the request and includes the request identifier on its response message back to the client.
  • The client keeps track of the identifier of its most recent request. The client waits for a response with the matching identifier.

Handling drops again

This version of the protocol correctly handles duplicate requests and responses, but unfortunately it is no longer as tolerant to dropped messages as before. In particular, consider again the scenario where a client's request is executed on the server but the server's response message is dropped. The client will retransmit its request, but since the server already executed the request, it will ignore the retransmitted request since it is a duplicate. The problem is the client is stuck because it never received the response. We'd like the server to retransmit its original response message to unblock the client.

So instead of tracking the set of executed request identifiers, we adjust the server to store a map from executed request identifier to a copy of the server's original response that request. When receiving a request, the server checks to see if the identifier is in the map. If so, it means the request was already executed, so the server just retransmits another copy of its original response found in the map. Otherwise, the request was not previously executed, so the server executes it for the first time, sends the response, and adds the (request identifier, response) pair to its map of executed requests.

RPC Protocol

Incorporating our changes to Naive RPC, we arrive at the folloinwg not-so-naive RPC protocol:

  • When the application layer wants to invoke an RPC, then the client sends a request message with a unique identifier, the procedure name, and argument values to the server. The unique identifier is chosen to be distinct from all identifiers the client has ever used before.
  • After sending a request message, the client waits for the response. While waiting, periodically retransmits the request with the same unique identifier.
  • When the server receives a request message, it checks if the unique identifier has been executed before. If so, then the server retransmits the same response it sent back the first time the request was executed. If not, then the server executes the requested procedure and sends back a response message with the same unique identifier as the request and the return value from the procedure.
  • When the client receives a response message, it checks to see whether it has the same unique identifier as the request it is waiting for, and if so, returns the value to the application layer. If the client is not waiting for a request or if the unique identifier doesn't match, then the client ignores the response message.
  • We (still) make the following assumptions:
    • Nodes do not fail.
    • The application layer will not invoke another RPC until it receives the return value from the previous RPC.

Let's now revisit the problematic scenarios above and confirm that this protocol correctly handles them.

  • If a request message is dropped and the client is still waiting for a response to that request, then the client will eventually retransmit the request message.
  • If a response message is dropped and the client is still waiting for a response, then the client will retransmit the request. When the retransmitted request arrives at the server, the server will observe that it has already executed the request, but it will retransmit the response to unblock the client.
  • If a request message is duplicated and delivered twice, the server will detect it using the unique identifiers. The server will retransmit a second copy of the response message, but that is not a problem because the client already handles duplicate response messages. (See below.)
  • If a response message is duplicated and delivered twice, the client will ignore the second copy of the message. If the second copy is delivered while the client is not waiting for a response, then it will be ignored. If the client is waiting for a response to a later request message, then the client will compare the unique identifiers and realize the response message is not the one it is looking for, and it will ignore it.

Reducing server space: version 1

As described, the protocol uses server memory proportional to the number of requests ever executed. This is because the server stores copies of all previous responses so that it can retransmit them if it receives another copy of the corresponding request. We can save space on the server by removing responses once they are no longer needed. The server only needs a response if it might need to retransmit it again in the future. Once the client has received the response, the server can stop storing a copy of it. To do this, the server needs to know that the client has received the response.

One way for the client to tell the server that it has received the response is to have the client send the server a new kind of message called an acknowledgment whenever it receives a response. The acknowledgment message contains the unique identifier of the corresponding response. When the server receives the acknowledgment, it can remove the saved copy of the response to reduce space usage.

To make this into a robust protocol, we would need to handle the situation where the acknowledgment message was dropped. We leave this as an exercise and move on to an even better way to design the protocol that avoids acknowledgment messages altogether.

Reducing server space: version 2

The client is only allowed to send one request at a time. So if the server receives a new request from the client, then that implicitly serves as an acknowledgment to the server that the client received its previous response.

We can optimize the protocol from the previous section using this insight to eliminate explicit acknowledgment messages as follows. Instead of using arbitrary unique identifiers for messages, we use ordered sequence numbers. The client identifies its messages with ascending sequence numbers. The server stores only the sequence number and response for the most recent client request it has executed. Whenever the serve receives a request, it handles it according to the following cases:

  • If the sequence number is greater than the most recently executed one, then this is a new request. The server executes the request, sends the response to the client, and stores the sequence number and a copy of the response. The server also removes all previously stored responses and sequence numbers.
  • If the sequence number is equal to the most recently executed one, then its possible the client is retransmitting its last request because the server's response was dropped. The server retransmits its stored response.
  • If the sequence number is less than the most recently executed one, then this is a duplicate of an old request. The server can safely ignore this duplicate because the client has already implicitly acknowledged the server's response to this request by sending a higher-numbered request.

With these adjustments, the server only needs to store the most recently executed request for the client, so the protocol's memory requirements do not grow over time.

Handling multiple clients

We can adapt the protocol to handle multiple clients on a single server. We assume that the network allows nodes to determine what other node sent it a particular message. Each client sends its requests to the one server, and each client has an independent space of sequence numbers.

First, what does it mean for the server to be correct in the presence of multiple clients? Each client is still required to only send one request at a time, but multiple clients can send requests at the same time. So there is not a single global total order on requests that we can use to describe the correct results. Instead, we take advantage of the fact that our system consists of a single server to determine what order the requests should be executed in.

Definition: Multi-Client Single-Server Sequential Correctness

If the system consists of multiple clients and one server, and neither the clients nor the server fail, and the clients each send a sequence of requests one at a time, waiting for each response before sending the next request, then the server responses agree with what would have happened if we had run the procedures locally in the order the requests first arrived at the server.

To implement this in our protocol, the server needs to store, for each client, the sequence number and response message for the most recent request executed for that client. The memory required by the server is now proportional to the number of clients who have ever executed a request.

Beyond a single server: Handling node failures

In this chapter, we have described what it takes for a client to reliably ask a server to do something for it, even in the presence of the standard network faults of dropped, duplicated, delayed, and reordered messages. However, we have assumed that the nodes involved do not fail. If the server crashes, then the clients in this chapter will have no choice but to wait until the human operator restores the server, probably by rebooting it. Also, unless non-volatile storage is used, the server will not retain any of its state from before the crash, meaning clients may have lost work and may not know whether their most recent request was executed or not.

We will spend the next several chapters discussing automatic mechanisms for handling server crashes through replication, which is the idea that having multiple equivalent servers allows the system to continue to operate even if one of the servers crashes. As we will see, this makes the protocols significantly more complex, not least because it requires defining a more sophisticated correctness property that does not depend on assuming their is only one server.
